## 0. 一页决策摘要

1. 全部章节 Know-how 先汇总去重，AI 自动编译规则并直接运行首版，不要求业务逐条预审。
2. 业务主要通过抽取结果、章节结果和 AI 审核问题发现 Know-how 编译缺漏，再修正规则并重新运行。
3. 每份底稿形成一个 Markdown；PDF 内部逐页转图，但不向业务暴露大量分页 Markdown。
4. 所有页面优先使用原生文字层；扫描页必须形成页图。可识别页面写入基础 Markdown，未全文识别的页面只在清单中记录状态，不得在业务可读 Markdown 中重复堆叠“尚未 OCR”占位文案。
5. Know-how 需要的页面使用视觉模型精读，覆盖对应 Markdown 并提取结构化数据；超长文件或模型超时时，至少返回与当前字段相关的页面摘要、页码和命中原文，不能以占位页作为一次“提取成功”。
6. 首期人工输入层只有“项目摘要”和“项目概况整表”两个逻辑输入槽；文件名由当前项目运行时识别，不写入共用 Know-how，也不混入 AI 抽取完成率。
7. 服务内采用关键事实级溯源；最终 Word 不显示来源、系统链接或审核标记。
8. 数据来源包括项目材料、两份人工输入源、天眼查 MCP 和网络搜索。
9. 来源冲突由 AI 自动选择当前使用值，但必须展示冲突、候选来源和选择理由，允许业务修正。
10. 首期重新生成直接覆盖对应章节/小节，不做人工修改保护。
11. 小节生成后自动进行 AI 审核；全文页面可主动运行全文审核。
12. AI 审核只提示问题、不阻止 Word 导出；业务对最终申报材料负责。
13. 每个小节的 Know-how 编译后形成三件可编辑、可执行产物：提取规则、生成 SKILL、审核 SKILL；保存这些产物后，下次抽取、生成或审核立即按新版本执行。
14. 所有小节的提取规则在模板包级汇总，字段 ID 或标准化语义相同的规则只保留一个标准字段，并记录被哪些小节使用；冲突规则必须显式提示，不能静默复制两份数据。
15. 报告生产同时提供“小节生成”和“整章生成”：整章生成按顺序批量执行本章所有已配置的小节 SKILL，未配置 Know-how 的小节明确跳过，不得回退到旧的大章 Agent。

## 1. 背景

业务人员会针对申报材料的每一章或每一小节编写 Know-how，说明：

- 需要读取哪些编号文件或外部数据源；
- 需要提取哪些事实、数字和描述；
- 表格与正文如何组织；
- 数据之间如何校验；
- 缺失、冲突和不适用情形如何处理；
- 最终报告应如何审核。

当前系统以章节 Agent 临时读取材料、调用工具和生成内容为主，存在以下问题：

1. 同一底稿可能被不同章节重复读取和重复抽取；
2. 扫描型 PDF 不能稳定提取，财报数值抽取尚未形成通用流程；
3. 抽取逻辑隐藏在代码或 Prompt 中，业务无法看见、验证和修改；
4. 纯人工填写项与材料抽取字段混在同一个数据页面；
5. 数据来源、正文语句和最终报告之间缺少稳定映射；
6. 当前“审核”偏向数据字段，实际业务更需要审核生成后的报告；
7. 最终 Word 应为干净终稿，不应携带系统链接或内部审核标记。

本项目拟将现有系统改造为“Know-how 驱动、材料一次解析、数据一次抽取、章节复用、报告可审核、过程可溯源”的申报材料生产平台。

## 2. 产品目标

### 2.1 核心目标

1. 业务提交全部章节 Know-how 后，系统自动生成并运行全局底稿清单、数据字典、抽取规则、人工输入要求、章节生成规则和报告审核规则；不要求业务在首次运行前逐条审核全部规则。
2. 同一版本的每份底稿原则上只解析一次；同一个事实原则上只抽取一次，供全部章节复用。
3. 每份文件面向业务和 Agent 形成一个连续 Markdown；PDF 分页图片仅作为内部读图、缓存和定位资产。
4. 数据中间层只保存从材料、天眼查或网络中抽取、计算、校验得到的事实，不承载纯人工填写项。
5. 业务可以查看每个字段“从哪里取、怎么定位、怎么抽取、怎么转换、如何校验”，并能修正项目值或提交规则修改建议。
6. 支持按整章或小节生成，生成时组合章节规则、文件 Markdown、数据中间层和人工输入。
7. 服务内支持正文和表格的可点击溯源；点击后可查看文件页码、命中原文、天眼查快照或网络页面。
8. AI 审核面向生成后的报告，检查事实依据、数字一致性、Know-how 完整性和格式要求。
9. 点击“生成终稿 Word”时输出无来源标记、无审核标记的正式文件，同时后台保留对应的数据和证据版本。

### 2.2 非目标

首期不实现：

- 任意行业、任意申报模板的完全通用化；
- 要求业务在首次运行前逐条审核全部 AI 生成规则；
- 对所有超长 PDF 无差别进行全量高成本视觉识别；
- 在最终 Word 中输出系统链接、引用角标或审核批注；
- 用网络搜索结果静默覆盖申报材料原件；
- 将业务 Know-how 中的示例值当成项目真实数据。

## 3. 关键产品决策

### 3.1 全部 Know-how 先汇总，再制定抽取计划

系统应先读取所有当前生效的章节 Know-how 自动版本或业务修订版本，形成全局数据需求并去重，再安排底稿解析和数据抽取。

```text
全部章节 Know-how
        ↓
全局底稿清单 + 全局数据需求
        ↓
按文件合并抽取任务
        ↓
每份底稿解析一次、每项数据抽取一次
        ↓
全部章节共同复用
```

新增或修改 Know-how 时，只补充或重跑受影响的文件、页面、字段和章节。

#### 3.1.1 可执行三件套

每个小节的 Know-how 必须编译为以下三个独立产物，而不是只保存一份不可读的模型返回 JSON：

1. `EXTRACTION_RULES.json`：该小节需要的字段、底稿角色、定位提示、提取策略、单位、校验和缺失策略；
2. `GENERATION_SKILL.md`：如何组合数据底座、单文件 Markdown 和人工输入形成本小节正文及表格；
3. `AUDIT_SKILL.md`：生成后应检查的事实、数字、来源、完整性和格式规则。

三件套均在 Skill 管理中可查看、编辑、保存和重置。编辑后的内容是执行源，不是说明文档：

- 提取规则保存后，下一次点击“提取数据”按新规则执行；
- 生成 SKILL 保存后，下一次生成或重新生成该小节按新规则执行；
- 审核 SKILL 保存后，下一次审核该小节按新清单执行。

Know-how 原文与编译产物分开保存。业务可使用“保存并编译”得到预览，确认后应用三件套；上传文件或只保存 Know-how 不自动发起耗时抽取。

#### 3.1.2 全局字段去重与合并

编译结果应用前，系统对全部小节的字段做全局归一化：

```text
稳定字段 ID 优先
  → 同 ID 合并 source/strategy/校验/使用小节
  → 无稳定 ID 时按“标准化字段名称 + 主体 + 时间口径 + 单位”判断等价
  → 可兼容差异合并为候选规则
  → 不可兼容差异生成规则冲突，要求业务选择
```

合并后的字段记录 `used_by_sections`。章节生成模板中的旧字段引用必须同步改写为标准字段 ID，不能出现“规则合并了但生成仍引用旧字段”的悬空状态。

### 3.2 对外一文件一 Markdown，对内逐页处理

业务和生成 Agent 读取的是一份文件对应的一份 `document.md`。扫描 PDF 在系统内部逐页转图片并识别，识别结果合并成一个连续 Markdown，Markdown 内保留页码锚点。

```markdown
<!-- page: 8 -->

## 合并资产负债表

单位：元
```

内部页图用于：

- 扫描件视觉识别；
- 单页重新识别；
- OCR/视觉结果缓存；
- 点击来源后跳页和高亮；
- 避免整份超长 PDF 一次性发送给模型。

### 3.3 数据中间层与人工输入分离

数据中间层包括：

- 文件原文直接抽取值；
- 表格结构化抽取值；
- 天眼查 MCP 查询结果；
- 网络搜索结果；
- 基于来源数据计算的派生值；
- 多来源交叉校验结果。

以下内容放入独立“业务人工输入”模块：

- 无可靠底稿来源的项目类型、联系人、联系方式等；
- 需要业务判断或撰写的说明；
- 业务明确要求人工填写的表格或字段。

业务上传的摘要表、项目概况表属于“人工输入源”。其值可以参与章节生产和交叉校验，但不应伪装成 AI 从证明材料中抽取的字段。

首期人工输入层只包含“项目摘要”和“项目概况整表”两个逻辑输入槽。润泽项目中的两份同名 Word 只是回归样本；其他项目可使用不同文件名，系统按表头特征识别并允许业务确认映射。

其他 Know-how 中出现但无法从材料、天眼查或网络取得的内容，首期在生成结果中按缺失策略提示，不自动扩展为新的人工输入表单。

### 3.4 数据层做纠错，报告层做审核

数据中间层提供：

- 抽取结果检查；
- 来源与命中原文查看；
- 项目级值修正；
- 规则修改建议；
- 冲突和低置信提示。

正式 AI 审核发生在章节或报告生成之后，审核对象是最终写作内容，而不是要求业务逐字段审批数据。

### 3.5 溯源只在服务内展示

服务内保存 `正文陈述 → 数据字段 → 来源证据` 映射。报告工作台展示来源标签并支持点击跳转。最终导出的 Word 不显示来源链接、引用角标、审核问题或内部注释。

首期采用“关键事实级溯源”：数字、日期、主体、股权、重要结论和表格单元格必须绑定来源；模板套话、过渡语和一般性表达不强制逐句绑定。

### 3.6 首期简化原则

- AI 编译 Know-how 后直接生成自动版本并运行，业务主要从实际抽取结果、生成结果和 AI 审核问题中反查规则缺漏；
- 规则和运行结果必须可回溯，业务发现问题后可修正规则并定点重跑，不要求首次运行前逐条确认；
- 来源冲突由 AI 自动选择当前使用值，同时必须展示冲突、备选值和选择理由；
- 首期重新生成允许覆盖原章节内容，暂不实现内容块锁定和人工修改保护；
- AI 审核不阻止 Word 导出，最终责任由业务承担；未处理问题随终稿版本在后台留档。
- 申报材料页每个大章标题行提供“生成本章”入口；一次点击依次生成本章全部已配置小节，汇总成功、失败和未配置跳过清单，成功后自动触发一次本章报告审核。小节入口保留用于定点查看、修改后重生成和复核。

## 5. Know-how 规则编译

### 5.1 输入

每个 Know-how 文件至少绑定：

- 模板包；
- 章节编号或小节编号；
- 文件版本；
- 业务编写人；
- 发布时间或状态。

Know-how 可以使用业务自然语言中的附件编号帮助人理解，但编译器不得把样例项目的编号、公司名、文件名、路径或具体年份固化成共用规则。例如：

> 从原始权益人各报告期财务报告的合并资产负债表读取资产总计和负债合计，以万元列示；从原始权益人运营情况承诺函读取近三年重大违法违规及安全生产事故承诺，无法确认时不得推测。

### 5.2 编译产物

每份 Know-how 由 AI 编译为三件套；底稿要求和字段抽取规则合并在 `EXTRACTION_RULES.json`，章节结构和人工输入引用合并在 `GENERATION_SKILL.md`，报告检查项写入 `AUDIT_SKILL.md`。下面五类信息仍必须完整表达，但不再作为五份彼此分散的文件。

#### A. 可复用的底稿角色与选择规则

```yaml
role_id: audit_reports
document_role: "原始权益人最近3个会计年度及一期财务报告"
selector:
  document_type: originator_financial_report
  filename_keywords_any: ["审计报告", "财务报表", "财务报告"]
  path_keywords_any: ["原始权益人", "审计的财务报告"]
  exclude_keywords_any: ["项目公司", "备考财务报表"]
  subject_ref: originator.company_name
repeat_by: reporting_periods
match_prompt: "按申报基准日展开 n-3、n-2、n-1、n，并为每期选择原始权益人报告。"
required: true
```

#### B. 数据抽取规则

```yaml
metric_id: finance.total_assets
field_name: 总资产
source_role: audit_reports
locator: 合并资产负债表/资产总计/期末余额
extract_method: financial_table_cell
target_unit: 万元
extract_prompt: "读取当期合并资产负债表最后一行资产总计；先识别表头单位，再换算为万元并保留两位小数。"
validation:
  - total_assets >= total_liabilities
missing_policy: mark_missing
```

抽取规则不维护“用到哪个章节”；字段使用关系由章节生成规则维护。

具体年份和文件只在项目运行时计划中出现，例如 `finance.total_assets.2023 → audit_report_2023 → 当前项目/某财务报告.pdf → 第9页`。运行时计划必须保存候选文件、得分/选择理由、实际路径、哈希、页码和所用 Prompt，但不得反向写回模板规则。

#### C. 人工输入 Schema

```yaml
input_id: project.contact
label: 项目联系人姓名及职务
type: string
required: true
section: "2.3"
```

#### D. 章节生成规则

```yaml
section_id: "2.3"
required_fields:
  - originator.company_name
  - finance.total_assets.*
document_queries:
  - source_role: originator_commitment
    query: "近三年重大违法违规和重大安全生产事故承诺"
manual_inputs:
  - project.contact
output_structure:
  - 基本信息
  - 财务状况
  - 违法违规和信用情况
```

#### E. 报告审核规则

```yaml
section_id: "2.3"
checks:
  - 所有关键工商事实必须有来源
  - 财务正文与表格数值一致
  - 不得使用Know-how示例值补缺
  - 信用查询必须说明查询时点
```

### 5.3 规则工作流

规则状态：

```text
AI 自动版本（立即运行） → 业务发现问题 → 业务修改 → 修订版本 → 重新运行 → 已废弃
```

AI 编译完成后生成不可变的自动版本号并立即用于试运行，不要求业务逐条预审。业务修改后生成新的修订版本，不能直接覆盖旧版本。每次抽取和章节生产必须绑定所用规则版本，保证可以从结果反查当时的 AI 规则和业务修改记录。

首期界面采用“保存并编译 → 预览三件套及合并报告 → 应用”的安全交互。应用完成只发布规则，不自动启动抽取；业务点击“提取数据”后，系统才按全部当前生效规则合并执行一次全局抽取。编译预览必须返回：

- 新增、修改、复用和合并的字段数量；
- 被合并的字段 ID 与标准字段 ID；
- 不能自动合并的规则冲突；
- 三件套的最终可编辑内容。

### 5.4 规则工作台能力

业务应能看到：

- Know-how 原文；
- AI 识别出的底稿清单；
- 字段名称与来源文件；
- 业务可读的定位、抽取、转换和校验逻辑；
- 对应机器规则；
- 当前规则在样例文件上的命中原文和测试结果；
- 修改前后差异；
- 发布和回滚记录。

业务修改分为两类：修改“材料怎么选、字段怎么取、单位怎么换、如何校验”属于模板级 Know-how 修订，会影响以后使用同一模板的不同项目；修改当前项目的事实值属于项目级人工覆盖，不得污染共用规则。业务点击“保存通用规则并在本项目重提取”后，系统先保存模板规则版本，再用当前项目目录重新匹配运行时文件；以实际命中文件为边界，重新构建该文件 Markdown，执行绑定到该文件的全部当前规则，最后统一更新关联字段。不能只改当前单元格，也不应无差别重跑全项目。业务人工覆盖值不被自动覆盖，但必须列入本次运行的保留清单。

每次按文件重提取必须记录：模板规则版本、当前项目运行批次、触发字段、实际文件路径及哈希、完整规则快照、候选文件与选择理由、关联字段、提取前后值、人工覆盖字段、开始/完成时间、状态和错误。规则已保存但重提取失败时，保留失败记录和新规则，允许修正规则后再次执行。

## 6. 来源接入与文档处理

### 6.1 来源类型

系统统一支持以下来源：

| 类型 | 说明 | 稳定定位 |
|---|---|---|
| document | 用户上传的 PDF、Word、Excel、图片等 | 文件编号、文件哈希、页码、原文锚点 |
| manual_input | 业务人工输入表或人工上传输入源 | 输入项、填写人、填写时间、版本 |
| tianyancha | 天眼查 MCP 查询 | 工具名、参数、企业 ID、查询时间、返回快照 |
| web | 网络搜索和网页读取 | 查询词、URL、访问时间、原文摘录、快照哈希 |

### 6.2 运行时文件映射

系统应理解 Know-how 中的 `X-X-X 文件` 写法，但编号只能作为候选线索，不能作为跨项目规则主键。输入当前项目目录后，系统按语义角色、主体、报告期间、文件名/目录关键词和排除词建立运行时映射：

```json
{
  "document_ref": "2-2-3",
  "filename": "润泽科技发展有限公司2023年审计报告.pdf",
  "relative_path": "一、参与主体情况/.../2-2-3 ...pdf",
  "sha256": "..."
}
```

存在同编号多文件、编号缺失、候选同分或名称冲突时，必须在“材料选择规则”中展示候选与当前选择；允许 AI 先按匹配 Prompt 选择并继续运行，但必须保留冲突供业务修改通用规则或确认项目映射。

### 6.3 文档包

每份材料形成一个文档包：

```text
documents/<document_id>/
├── manifest.json
├── document.md
├── tables.json
└── pages/
    ├── page-001.png
    ├── page-001.json
    ├── page-002.png
    └── page-002.json
```

原始材料继续保存在项目 materials 目录，文档包只保存安全引用和解析产物。

### 6.4 文档处理策略

#### Word/Excel

- 保留标题、段落、表格和工作表结构；
- 按正文顺序输出 Markdown；
- 表格同时输出 Markdown 和结构化 JSON；
- 保留单元格定位信息。

#### 原生文字层 PDF

- 直接提取文字和坐标；
- 修复中文断行；
- 识别标题、段落和表格；
- 合并为一个 `document.md`；
- 保留页码锚点。

#### 扫描型 PDF

1. 每页转为图片；
2. 有本地 OCR 时，先用本地 OCR 形成全文基础 Markdown；
3. 没有本地 OCR 或单页识别失败时，保留页码和原始图片，并在 manifest 中记录 `image_only/failed`；业务可读 `document.md` 只合并连续状态摘要，不逐页输出相同占位句；
4. 根据 Know-how 定位需要精读的页面，通过视觉模型读取并覆盖对应 Markdown；
5. 视觉精读同时输出 Markdown、表格 JSON、关键字段候选和坐标；
6. 合并成一个 `document.md`；
7. 支持单页重新识别；
8. 一个必要文件只有在“所需字段已提取或已给出明确缺失结论”后才算完成，单纯生成页图或占位 Markdown 不算完成。

#### 超长 PDF

默认采用两阶段策略：

1. 全部页面建立图片和轻量索引；
2. 有原生文字层则直接形成基础 Markdown；无文字层且存在本地 OCR 时，用本地 OCR 形成基础 Markdown；
3. 根据全局 Know-how 需求，对目标页面进行视觉模型高精度识别，并覆盖基础结果。

如果模型调用超时或一次无法处理全部页面，系统允许只完成与当前 Know-how 字段相关的页面和摘要，但任务结果必须列出已读页、未读页、失败原因和受影响字段，不得用重复占位文案伪装成完整 Markdown。

系统可提供业务主动触发的“全文高精度识别”，但首期不默认执行。

### 6.5 文档解析缓存

缓存键至少包括：

```text
文件 SHA256 + 解析器版本 + OCR/视觉模型版本 + 页面处理参数
```

缓存未变化时不重新解析；只修改某一页识别规则时，只重跑该页。

## 7. 统一检索与数据中间层

章节生成和抽取规则通过统一检索接口访问：

- 结构化字段精确检索；
- 文件 Markdown 全文检索；
- 文件编号与标题定位；
- 页码和原文锚点定位；
- 天眼查查询快照检索；
- 网络查询快照检索。

首期可采用字段查询 + 全文检索；向量检索作为后续增强，不作为首期依赖。

### 7.4 数据来源冲突

系统不在首期硬编码唯一来源优先级。出现多个来源不一致时，由 AI 结合 Know-how、材料性质、查询时点、来源权威性和字段语义自动选择当前使用值，但必须同时保存并展示：

- 当前选择值和来源；
- 其他候选值和来源；
- 冲突内容；
- AI 选择理由；
- 查询或文件时点。

来源冲突必须在报告 AI 审核中提示。AI 的自动选择允许业务直接修改，不能删除其他候选证据。

### 7.5 项目纠错与规则反馈

业务可以进行两类操作：

1. **项目值修正**：仅影响当前项目，保留原始抽取值、修正人和修正时间；
2. **规则调整建议**：记录当前规则、问题描述、业务建议和正确示例，由规则管理员决定是否发布新版本。

项目值修正不能覆盖或删除原始证据。

## 8. 业务人工输入

业务人工输入为独立模块，不出现在“AI 抽取字段完成率”和“PDF 抽取失败”统计中。首期固定为“项目摘要”和“项目概况整表”两个逻辑输入槽，不固定文件名。

首期人工输入支持：

- 字符串、日期、数值、枚举、富文本和表格；
- 从业务摘要表、项目概况表导入；
- 读取并展示两份既有 Word 输入表；
- 字段必填检查；
- 填写人和更新时间；
- 版本记录。

第一章项目概况表如业务要求“整表直接复制”，系统应将其作为人工输入源完整保留，不通过模型改写。

## 9. 章节生产

### 9.1 生产粒度

支持：

- 生成整章；
- 生成一个二级小节；
- 重新生成一个小节并覆盖该小节现有内容；
- 仅刷新结构化表格；
- 仅刷新引用了变化字段的正文块。

### 9.2 章节生产包

每次生成前组装不可变的生产包：

```json
{
  "section_id": "2.3",
  "generation_rule_version": "gen-v2",
  "data_snapshot_id": "data-v5",
  "manual_input_version": "manual-v3",
  "document_refs": ["1-1", "2-2-1", "2-2-2", "2-2-3", "2-2-4", "3-1", "4-1"],
  "external_snapshot_ids": ["snapshot-tyc-001"],
  "template_version": "ndrc-2024-v1"
}
```

生成 Agent 只读取生产包内的数据和材料，不在生成阶段无计划地重新扫描项目全部文件。

### 9.3 生成输出协议

生成结果不能只有纯文本，必须同步输出 Claim 与来源映射。

```json
{
  "section_id": "2.3",
  "blocks": [
    {
      "block_id": "block-001",
      "type": "paragraph",
      "text": "润泽科技发展有限公司成立于……",
      "claims": [
        {
          "claim_id": "claim-001",
          "text": "润泽科技发展有限公司成立于……",
          "field_refs": ["originator.established_date"],
          "evidence_refs": ["evidence-license-001"]
        }
      ]
    }
  ]
}
```

### 9.4 缺失与冲突处理

- 必需数据缺失时按 Know-how 的缺失策略处理；
- 不允许用 Know-how 示例值补缺；
- 来源冲突时由 AI 自动选择当前使用值，并将冲突、候选值和选择理由送入报告审核；
- 低置信扫描件数字应保留原始识别结果并在报告审核中提示；
- 人工输入缺失时在报告工作台提示，不写入虚构内容。

## 10. 服务内溯源

### 10.1 展示方式

报告工作台不再以“一段/一节一组来源”作为主展示。系统应在关键事实文字后显示可点击引用号，表格按单元格显示，例如：

```text
润泽科技发展有限公司成立于2009年8月13日〈可点击引用号〉。
表格：总资产 | 2,868,836.57〈可点击引用号〉
```

生成块保存结构化 `provenance`：正文保存事实在段落中的 `start/end`、字段 ID、展示值和来源列表；两列表保存到行值；财务表保存与单元格对齐的 `cell_provenance`。行政区划合并、单位换算、四至截取等生成变换必须保留多来源和处理公式。旧 `src` 字段仅作兼容回退。

材料回查时，抽取证据中已保存的 PDF 物理页码属于确定性定位，优先级高于打开文件时执行的全文摘录搜索；只有证据未保存页码时才允许全文精确/模糊搜索决定跳转页，避免财务数字在附注中重复出现时跳到错误的后续页面。

### 10.2 点击行为

| 来源 | 点击行为 |
|---|---|
| 申报材料 | 打开文件预览，跳转到页码，并高亮或定位命中原文 |
| 文件 Markdown | 打开对应文件 Markdown，定位到标题或段落 |
| 天眼查 MCP | 打开本次查询快照，可继续跳转天眼查公司页面 |
| 网络搜索 | 展示保存摘录、查询时间和原始 URL |
| 人工输入 | 展示输入项、填写人、填写时间和版本 |

### 10.3 反向查询

系统同时支持：

- 从正文陈述查看字段和证据；
- 从字段查看所有使用该字段的章节；
- 从来源文件查看其支持了哪些字段和正文陈述；
- 从审核问题跳转到具体正文块及来源。

## 11. AI 报告审核

### 11.1 审核对象

AI 审核面向已生成的小节、章节或整份报告，不面向数据中间层字段逐项审批。

### 11.2 审核类型

#### 事实依据审核

- 关键事实是否有 Evidence；
- Evidence 原文是否支持当前陈述；
- 是否存在无来源推断；
- 是否使用了 Know-how 示例值；
- 天眼查和网络信息是否标记查询时点。

#### 数据一致性审核

- 正文与表格是否一致；
- 不同章节引用同一字段时是否一致；
- 原始单位和目标单位转换是否正确；
- 公式计算是否正确；
- 报告期和申报基准日是否一致。

#### Know-how 完整性审核

- 要求的段落和表格是否齐全；
- 要求读取的底稿是否实际使用；
- 缺失内容是否按规定处理；
- 禁止性表述是否出现。

#### 来源质量审核

- AI 选择当前来源的理由是否充分；
- 当前使用值是否与其引用来源一致；
- 来源冲突是否披露；
- 候选来源及查询时点是否完整保留；
- 网络来源是否为官方或权威来源。

#### 格式审核

- 标题层级、编号和顺序；
- 表格结构和表名；
- 模板字段完整性；
- Word 渲染格式。

### 11.3 审核问题模型

```json
{
  "issue_id": "audit-001",
  "section_id": "2.3",
  "block_id": "block-001",
  "type": "unsupported_claim",
  "severity": "error",
  "message": "无重大违法违规结论缺少承诺函原文支持",
  "evidence_refs": [],
  "suggested_action": "补充4-1文件证据或删除该结论",
  "status": "open"
}
```

审核结果以问题清单呈现。业务可修改报告、忽略问题、重新生成或直接导出 Word；AI 审核不阻止导出，也不代表业务审批结论。AI 不应在审核阶段静默改写报告内容。

### 11.4 AI 审核的产品位置与触发时机

AI 审核放在“章节生产之后、终稿导出之前”的报告工作台中，不放在数据中间层。

首期包含两个入口：

1. **小节审核**：每次生成或重新生成小节后自动运行，在小节编辑区右侧抽屉或下方问题面板展示；问题可点击定位到正文块、字段和来源。
2. **全文审核**：在全文预览/终稿页面提供“运行 AI 审核”按钮，检查跨章节一致性、缺漏和格式问题。

页面顶部显示问题汇总，例如“3 个严重问题、8 个一般提示”，但“生成终稿 Word”按钮始终可用。导出时不弹出阻断审批，只将尚未处理的问题数量和审核快照记录到终稿版本。

每个小节审核结果必须绑定真实 `section_id`、正文块或表格位置以及相关字段/证据。问题卡片提供“重新生成该小节”；点击后只覆盖该小节，随后自动重新审核。跨小节问题若能识别一个或多个相关小节，应分别提供定向跳转/重生成入口；无法可靠识别时只展示人工复核提示，不盲目重生成整章。

## 12. 终稿 Word

### 12.1 导出原则

最终 Word：

- 不显示来源标签；
- 不显示系统 URL；
- 不显示审核问题；
- 不显示内部字段 ID；
- 不显示 Know-how 或 Prompt；
- 严格使用正式模板和已确认内容。

### 12.2 终稿版本记录

每次生成 Word 时保存：

- 报告版本；
- 生成时间和操作人；
- Know-how/规则版本；
- 数据快照版本；
- 人工输入版本；
- 外部查询快照版本；
- 报告审核结果；
- Word 文件哈希和存储路径。

即使 Word 中没有来源，服务仍能打开对应终稿版本，查看当时的正文、字段和证据映射。

- 一文件一 Markdown；

- 页面类型、识别方式和错误信息；
- 单页重新识别；

不展示纯人工填写项，不使用“字段审核通过率”作为核心指标。

### 13.5 章节生产中心

- 按章/按节生产按钮；

## 15. 任务状态与错误处理

文档解析、视觉识别、抽取、章节生成和报告审核均为可恢复任务：

```text
pending → running → completed
                  ↘ partial
                  ↘ failed
```

任务必须记录：

- 输入版本；
- 开始/结束时间；
- 当前文件和页面；
- 成功、失败和跳过数量；
- 模型和工具；
- 费用/Token/耗时；
- 可重试错误；
- 结果快照。

单个文件或页面失败不应导致全部项目结果丢失。

## 16. 缓存与增量更新

### 16.1 文件级缓存

文件哈希未变化且解析器版本未变化时，不重新解析。

### 16.2 页面级缓存

页面图片、视觉模型版本和识别参数未变化时，不重新读图。

### 16.3 字段级缓存

来源证据、抽取规则和转换规则未变化时，不重新抽取。

### 16.4 外部数据缓存

天眼查和网络结果按以下维度缓存：

```text
来源类型 + 工具/查询词 + 参数 + 查询时点/有效期
```

外部结果超过有效期后标记“需更新”，不静默覆盖旧快照。

### 16.5 章节级缓存

章节生产包未变化时，不自动重新生成。数据变化时提示受影响章节，由业务选择定点刷新；首期刷新或重新生成时直接覆盖对应章节/小节内容，不实现人工修改保护。

## 17. 权限、安全与合规

- 项目文件、Markdown、数据字段、查询快照和报告按项目权限隔离；
- 模型密钥、天眼查密钥仅从环境变量读取，不写入项目数据；
- 对外部模型发送材料前记录模型、页面和调用时间；
- 网络和天眼查结果保存必要快照，避免仅依赖实时页面；
- 业务修正、规则发布、报告修改和 Word 导出均记录操作日志；
- 来源预览接口必须校验项目权限和路径边界；
- 最终 Word 不暴露内部服务地址或字段 ID。

## 20. 首期验收标准

### 20.1 Know-how 与规则

- 两份业务 Know-how 能映射为底稿、抽取、人工输入、生成和审核规则；
- 每个小节可以查看和编辑 `EXTRACTION_RULES.json`、`GENERATION_SKILL.md`、`AUDIT_SKILL.md`，保存后分别影响下一次抽取、生成和审核；
- 多个小节声明同一字段时只形成一个标准字段，并在编译预览中显示合并关系和 `used_by_sections`；
- AI 生成的规则无需逐条预审即可自动运行，业务能从结果反查并修改抽取逻辑；
- 规则修改后可在真实材料上重新测试；
- Know-how 示例内容不进入项目数据。

### 20.2 文档解析

- 每份材料生成一个可连续阅读的 Markdown；
- 扫描 PDF 内部逐页转图并能通过视觉模型识别；
- Markdown 保留页码定位；
- 文件未变化时不会重复解析；
- 单页识别错误可以定点重跑。
- 必要底稿的业务可读 Markdown 不重复出现“本页为扫描页，尚未执行本地 OCR”类占位句；超时或未读页面在文档状态摘要中集中列示。

### 20.3 数据中间层

- 纯人工填写项不出现在数据中间层；
- 每个结构化数据均能查看来源、页码、原文和提取逻辑；
- 财务数字能查看原始单位、转换步骤和最终单位；
- 营业执照和财报 PDF 的目标字段不再全部为空；
- 点击一次“提取数据”会遍历当前生效规则涉及的每一份必要底稿；可提取字段应得到值，确无值时必须保存已检查的文件/页码和明确缺失原因，而不是无说明空白；
- 业务能修正项目值并提交规则调整建议；
- 同一字段被多个章节复用时只保存一份标准值。

### 20.4 章节生产

- 第一章第一节和第二章第三节可以分别生成；
- 项目概况表按业务要求直接使用人工输入源；
- 生成时不重复扫描全部原始文件；
- 正文和表格在服务内可以点击查看来源；
- 数据变化时能够识别受影响章节并定点覆盖刷新。

### 20.5 报告审核与 Word

- 小节生成后自动运行小节审核，全文预览页支持主动运行全文审核；
- AI 能识别无来源陈述、正文表格不一致、单位错误和 Know-how 遗漏；
- 审核问题可以定位到具体正文块和来源；
- 小节审核问题可以一键重新生成对应小节，并在生成后自动再次审核；
- 未处理审核问题不阻止 Word 导出；
- Word 导出不包含来源链接、审核标记或系统内部字段；
- 服务保存终稿对应的规则、数据、人工输入和来源快照版本。
